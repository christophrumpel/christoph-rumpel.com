## The App I Always Wanted To Build

For big tournaments like the World Cup or the Euros, my friends and I always bet against each other. Who wins the match, what is the score, who is the top scorer, all of that. We have been doing this for over twenty years now, and it is one of the most fun parts of every tournament.

But in all these years, we used `dozens` of different apps for it. And none of them was ever really good. Every time I thought the same thing: I could build this so much better myself.

So this time, I finally did it. The app is called **Bet Your Goal**, and this is the story of how it got built.

## Every Side Project Needs Goals

Whenever I start a side project, I set myself a few goals. It is never just about the app. It is about what I want to `learn` along the way. For this one, I had three goals:

**Write everything myself, by hand.** At work I do not write that much code anymore, and I missed it. So this project was my excuse to code again. No shortcuts.

**Learn a new stack.** I wanted to properly use `Inertia` and `React`, two things I had not worked with much before.

**Build something event-driven.** I wanted to try an event-sourced application with the [Verbs](https://verbs.thunk.dev) package. That was completely new territory for me.

And that is exactly how I built the first half of the app. Maybe around fifty percent. One hour every night, after a long day, whenever I found the time. It was slow, but it was fun. I learned a ton about events, about Verbs, about the whole stack. Exactly what I wanted.

## Then The AI Shift Happened

But this project ran over a couple of months. And in those months, something big happened.

All these AI tools and agents got `so good`, so fast. It was impossible to ignore. And for me, it was not only exciting as a developer, it was also important for my work at Laravel. I need to be on top of what is going on. What tools are developers using? How are they actually working now?

So at some point, I made a decision. I changed the goal of the project.

Instead of writing the rest myself, I would let AI write the code. Every line. And my new goal became learning what that actually feels like. How do you review code you did not write? Which tools work? What is the workflow?

This is where the `vibes vs. agent` part of the title comes in. The first half of Bet Your Goal was handcrafted. The second half was built with agents. And living on both sides of that line in one project taught me more than either half could on its own.

## The Tools I Used

I started with the most common ones. `Claude Code` and `Codex`, both a lot in the terminal.

Then I moved more and more to two tools that I really ended up loving:

[Polyscope](#) by BeyondCode is very chat-driven. You describe a new feature, and it just goes and builds it. It spins up its own workspaces, so you can work on multiple features at the same time without them interfering with each other. That was a completely different way of working for me.

[Solo](#) by Aaron Francis goes another direction. It is more about the agents that already live inside the app working `together`. There is an MCP server that lets them communicate with each other, which opens up a lot of possibilities.

Both are quite different from what I would normally use, like PhpStorm. But that was kind of the point.

I also tried designing with Claude for the first time, and I was really amazed. The results were already good out of the box. I still made a lot of changes to make the designs feel like `mine`, but the starting point was strong.

One thing to be aware of: some people can already recognize the patterns Claude tends to reach for in a design. But honestly, that is always the case unless you build a super custom design yourself, and you can only really do that if you are a good designer. I am not, and I did not mind.

## Reviewing Became The Actual Job

Here is the biggest change for me. Reviewing code became a huge part of my work, and I had basically never done it like this before.

Instead of writing code, you now read code that you did not write. And let me tell you, it is `exhausting`. It is a completely different skill, and at the beginning it was really hard. I got a lot better at it over time, but it is still difficult.

And there is another thing nobody warns you about. When you review AI code, there is a good chance you end up reading code you do not even understand. That almost never happens when you write it yourself. But AI might reach for different patterns, different tools, or even a different language than you would.

In my case, that language was `React`. My front end is React, and I did not have a good understanding of it. But suddenly I had to review a lot of React code.

So I had a choice. Learn enough React to properly review all of it, which would have taken forever and was not realistic. Or accept the React code without fully reviewing it.

I went with the second option. And I will be honest, that was really hard for me. I am still not sure it was the right call. But that is what I did, and it worked out really well.

A couple of things helped me a lot with reviewing:

Polyscope has a really nice view where you see all the changes, mark them as viewed, and even talk to the agents (which run on your own machine) about the changes. You can ask them to adjust things right there. Having a conversation while reviewing helped a lot.

And along the way, I built a side project of my side project. It is called **Walk My PR**. You feed it a GitHub pull request URL, and it analyzes the PR and gives you a summary. But the best part is that it `groups` the changes into steps. This group of changes was for this, those files were changed because of that. Just looking at a raw diff, it was often hard to see what was happening and `why`. The grouping makes reviewing so much easier.

## What I Learned

A few things really stuck with me after building this.

**AI can already write better code than I can.** And of course, faster. That was humbling, but also freeing.

**When the AI is fast, it does not mean you are fast.** Now `you` are the bottleneck. The AI can write a feature in five minutes, but it still takes me thirty minutes or longer to review it. The work just moves somewhere else.

**There is no single tool.** You have to work with a couple of different ones, test them, and find out what fits you. I ended up using different tools for different jobs. Bigger research and exploration, clearly defined features, quick easy changes. Each had its own best fit for me.

## It Is Live

The app is live now. It has been running for almost a month, and we already have over `400 users`. It is not a huge application, but it is heavily used, and that is what makes me happy. People are actually using it. And I use it every single day myself. I still ship something new to it almost daily.

One more thing I want to mention: it runs on [Laravel Cloud](https://cloud.laravel.com) with `managed queues`, which has been really great to work with.
